## 2. 项目的一句话定义

**Dyadic Force 是一个基于 Godot 2D 物理系统的本地双人协作滚球任务：两名参与者位于球体直径两端，通过连续方向输入在轮缘施力，共同控制球体平移与旋转；游戏同时记录可重算的输入、物理状态和事件数据，用于研究双人协调、补偿、领导关系与路线协商。**

这句话包含四个核心层面：

1. **任务层**：双人合力滚球，而非轮流操作或角色分工菜单；
2. **物理层**：连续施力、摩擦、惯性和扭矩，而非直接设置速度；
3. **体验层**：合作反馈优先，不展示个人贡献排名；
4. **研究层**：原始数据不可覆盖，派生指标可重算。

## 3. 从零搭建到预实验的开发时间线

### 3.1 2026-08-01：核心原型

**目标**

- 验证“两只猴子位于大球两端、共同推动球体”的核心交互；
- 用 2D 技术营造像素伪 3D 球体滚动；
- 建立双人分屏和基础场景。

**关键实现**

- Godot 4.6、GDScript、`RigidBody2D`；
- P1 使用 WASD，P2 使用方向键；
- 同向输入推动平移，反向输入诱发旋转；
- `pixel_ball.gdshader` 根据球体姿态更新表面纹理；
- 左右分屏分别跟随两名玩家；
- Sprout Lands 像素素材构成草地、围栏、水面与 UI。

**Git 证据**

- `6b46775`：初始双猴滚球与分屏原型。

### 3.2 2026-08-02：完整游戏流程

**目标**

- 从单场景原型扩展为可重复游玩的完整流程；
- 增加练习关、正式关、生命、计时、终点和结算。

**关键实现**

- `GameState`、`InputHub`、`SceneDirector` autoload；
- `LevelDef` 数据资源与通用 `level.tscn`；
- 标题 → 配对 → 选关 → 关卡 → 结算；
- 练习关不限时，正式关具有生命和倒计时；
- 结算展示共同轨迹、碰撞和结果，不做个人贡献排名。

**设计意义**

- 系统从“技术演示”转为可承载重复试次的任务平台；
- 数据驱动关卡结构为后续五关重构提供基础。

**Git 证据**

- `7e0ed54`：关卡流程与 Sprout Lands UI；
- `acbd447`：死亡、撞击伤害和像素 UI 细化。

### 3.3 2026-08-03：反馈抛光与合作物理

**主要问题**

- 传送门演出遮挡球体、视觉结构廉价；
- 地面箭头与真实路线方向不一致；
- 单人仍可能拖着另一人移动；
- 隐藏的“合作增益倍率”缺乏物理可解释性。

**最终决策**

- 放弃直接速度控制和不可感知的合作倍率；
- 使用接触点施力，让同一股力自然产生平移与扭矩；
- 闲置玩家通过轮缘摩擦形成可解释阻力；
- 结算仍坚持 dyadic feedback，不显示“谁贡献更多”；
- 重做独立传送特效层和轨迹内容包围盒。

**可用于论文的设计原则**

> 合作必要性不应依赖隐藏倍率，而应来自参与者能够感知和理解的物理耦合。

**Git 证据**

- `de48c54`：传送流程、结算 UI 与协作球物理。

### 3.4 2026-08-04：输入、校准、触觉和初版实验管线

**输入与设备**

- 支持 Switch Pro、Xbox、双键盘；
- Nintendo 与 Xbox 面键语义分别处理；
- 菜单支持手柄全流程操作；
- 方向提示由八方向吸附改为 360° 连续显示。

**连续力映射**

- 径向死区 `d=0.12`；
- 幂次响应 `γ=1.6`；
- 满幅输入对应 `Fmax=8.0` 游戏力单位；
- 不用离散档位惩罚满推，满推代价来自惯性、碰撞与精细控制需求。

**校准**

- 每次连接会话进行静置与绕圈校准；
- 漂移过大时判定校准失败；
- 原始轴、校准轴、死区后幅度、曲线后幅度和最终力分层记录。

**触觉反馈**

- 建立 `HapticHub`；
- 最终采用“扣血事件触发震动”，而不是按速度突变猜测碰撞；
- 删除会造成 Switch Pro 持续重启震动的移动微震；
- HP 改为 0.5 的离散步进，避免视觉心数和实际生命不一致。

**初版研究设计**

- 曾采用全局 `baseline` / `perturbation` 条件；
- 第 3 关在时间窗中交替削减某一侧输入增益；
- 初版日志包含逐帧输入、物理状态、路线误差与事件；
- 已开始计算方向一致性、启动差、互相关、补偿和恢复。

**Git 证据**

- `9f01d7c`：力校准、伤害震动和半心生命；
- `bb717ba`：暂停菜单、传送门震动和结算打磨。

### 3.5 2026-08-09：实验模式、调试模式和关卡扩展

**平台化目标**

- 实验模式与普通试玩分离；
- 普通试玩不写实验 CSV；
- 调试模式只在教学关显示物理参数面板；
- 调参结果写入独立配置，不污染进度。

**UI 演进**

- 修复选关页文本重叠；
- 防止 A/B 输入相同编号；
- 结算页只显示保存状态和打开文件夹；
- 物理调试参数由 21 个精简至 8 个；
- 调参说明从机械式“想怎样就调什么”改为自然的使用场景说明。

**关卡演进**

- 增加第 4、5 关；
- L4/L5 初版因复用旧关卡骨架、通道过窄而被否决；
- 第二版改为折返场和螺旋场；

**历史意义**

- 该阶段说明关卡并非一次成型；
- 用户体验反馈直接推翻了“仅换参数和装饰”的低成本扩展。

### 3.6 2026-08-13 至 08-14：五关重构与实验组件

**五类目标行为**

1. 第 1 关：共同起步；
2. 第 2 关：共同减速；
3. 第 3 关：弯道协调；
4. 第 4 关：失衡补偿；
5. 第 5 关：路线选择。

**核心设计约束**

- 每关只集中诱发一种主要合作行为；
- 关卡首先应像连续游戏，而不是实验任务拼盘；
- 除可撞门外，不新增玩家必须学习的可见实验物体；
- 路段、扰动和岔路追踪均在后台不可见；
- 不向玩家显示同步率、领导者、受扰者或风险标签。

**新增组件**

- `BreakableGate`：以速度、双方活动比例和方向一致性判断共同撞门；
- `RouteSegmentZone`：不可见路段标注；
- `PerturbationController`：第 4 关隐藏输入增益扰动；
- `ChoiceForkTracker`：记录第 5 关初始偏好、冲突、最终选择和反转；
- `CollisionCategory`：区分普通障碍、门和边界，使门可免伤。

**关卡重构结果**

- 第 3、4、5 关改为样条路线，避免直角拐；
- 第 3 关形成左右弯样本和恢复段；
- 第 4 关使用宽路与连续干扰；
- 第 5 关形成短窄与长宽路线的真实取舍；
- 第 1、3、5 关复用门作为合作节奏点。

**Git 证据**

**新手试玩反馈**

- 键盘调试低估了手柄下的门难度；
- 教学关没有门，正式第 1 关混入规则学习；
- 第 3–5 关 120 秒时限不足。

**已实施但仍需完整验证的调整**

- 第 3–5 关时限改为 180 秒；
- 静态检查无错误，但该轮未执行 Godot headless 测试。

**性能风险**

- `end_trial()` 在判定物理帧同步执行 flush 和全 session 派生分析；
- 会重读原始数据、计算互相关并写多份结果文件；
- 卡顿发生在通关或失败的高显著性时刻；
- 根因已经定位，但对话记录中尚未完成异步或增量修复。

**方法学意义**

> 数据采集管线不应在试次边界引入可感知延迟，否则基础设施本身会改变任务体验，并可能污染时间结构。

## 4. 研究对象与核心交互的操作化

### 4.1 双人协作不是两个独立角色

两名玩家不分别完成不同子任务，而是同时作用于同一个物理对象。球体同时整合双方的：

- 输入方向；
- 输入幅度；
- 接触点；
- 力矩；
- 静摩擦与动摩擦；
- 惯性和碰撞反馈。

因此，行为结果天然属于 dyad 层级，不能简单拆成两个独立个体分数。

### 4.2 同向、反向与失配

- **大体同向**：合力推动球体平移；
- **近似反向**：合力抵消但力矩增强，球体更偏向原地旋转；
- **方向失配**：产生侧向偏移、旋转或打滑；
- **一方闲置**：闲置侧的接触摩擦增加另一方单独拖动的成本。

### 4.3 为什么使用连续力输入

连续输入能保留：

- 启动力度；
- 中段细调；
- 同步启动差；
- 力度不对称；
- 方向冲突；
- 扰动后的连续补偿轨迹。

离散按键等级或直接设速会压缩这些行为差异，不利于研究协调过程。

### 4.4 为什么不显示个人贡献排名

结算页刻意呈现：

- 共同轨迹；
- 共同完成情况；
- 生命与时间；
- 碰撞和整体稳定性。

系统不向参与者展示：

- A/B 输入总量排名；
- 个人贡献百分比；
- 谁是领导者；
- 谁导致失败。

这既维持合作体验，也避免反馈反过来改变后续试次中的竞争动机。

## 5. 五关设计及其研究用途

### 5.1 教学关：建立共同心智模型

**当前用途**

- 学习同向推动；
- 学习反向旋转；
- 学习转弯前减速；
- 理解普通碰撞会受伤；
- 理解需要停在传送门上；
- 通过低难度门学习共同加速撞门。

**方法学作用**

- 把规则学习尽量移出正式试次；
- 可作为熟悉程度和初始能力参考；
- 不与正式关主要指标直接混合。

### 5.2 第 1 关：共同起步

**任务结构**

- 多次直线加速；
- 三扇规则一致、难度温和的可撞门；
- 失败撞门不扣血，代价主要是时间和重新组织。

**可测行为**

- A/B 启动时间差；
- 双方共同活动时长；
- 方向余弦；
- 力度差；
- 每扇门尝试次数与首次成功；
- 谁更常率先发起冲刺；
- 门 1 到门 3 的学习趋势。

**重要修正**

- 原三门递增和后续关卡复用最高难度的方案，对手柄新手过难；
- 现阶段已统一降低，但仍需双人手柄实测。

### 5.3 第 2 关：共同减速

**任务结构**

- 长直道建立速度；
- 两次回转迫使共同减速；
- 不增加停车台、门、分叉或扰动。

**可测行为**

- 入弯速度；
- A/B 开始减小输入的时点；
- 反向制动起点；
- 制动启动差；
- 过冲距离；
- 外侧碰撞；
- 出弯恢复时间；
- 谁先发起有效制动。

### 5.4 第 3 关：弯道协调

**任务结构**

- 样条生成的连续林间路线；
- 左右弯数量接近平衡；
- 不规则直道与恢复段；
- 门仅作为已学机制的节奏点。

**可测行为**

- 各弯转向起点差；
- 弯中方向一致性；
- 平均与峰值路线误差；
- 出弯过冲；
- A/B 纠偏贡献；
- 左右弯领导者；
- 领导权切换率和稳定性。

**解释边界**

- 第 3 关是正常协调参考；
- 不能被称为第 4 关的严格 baseline。

### 5.5 第 4 关：失衡补偿

**任务结构**

- 宽阔路线，减少地图本身的高难操作；
- 第 4 关固定真实干扰；
- 输入增益下降并带侧偏；
- A/B 按可复现序列交替受扰；
- HUD 告知本关存在干扰，但不显示受扰者。

**当前扰动协议**

- 单次约 10–14 秒；
- 间隔约 0.8 秒；
- 目标覆盖整段 120 秒原始时限设计；
- 输入增益约 0.45–0.60；
- 重生后短暂停顿再恢复扰动；
- 每次干扰前 200 ms 作为局部基线。

**注意**

- 关卡时限和扰动覆盖长度近期发生过调整，正式收数前需要冻结一致版本；
- 需求文档中仍可能残留“候选路段触发”和“连续时间循环”的历史混合描述，应以冻结协议和实际代码为准。

**核心指标**

- 未受扰者补偿反应时；
- 补偿方向准确度和峰值；
- 最大路线偏差；
- 恢复时间与右删失；
- 过度补偿和往返纠偏；
- 扰动前后领导者变化；
- 被扰者恢复后搭档撤力时点。

### 5.6 第 5 关：路线选择

**任务结构**

- 两个主要岔路；
- 每次都在短窄路线与长宽路线之间选择；
- 两条路最终汇合，不影响能否完成；
- 第二个岔路交换短路方向，降低方向和键位偏好；
- 不显示投票框、风险标签、宝箱或分数奖励。

**可测行为**

- A/B 初始持续输入偏好；
- 初始一致率；
- 冲突持续时间；
- 最终路线；
- 谁先改变方向；
- 谁的初始偏好成为最终选择；
- 分支反转；
- 当前生命、时间和前序碰撞对选择的影响。

### 6.1 引擎与场景

```text
设备原始轴
→ 每设备校准
→ 径向死区
→ γ 响应曲线
→ 条件增益
→ 虚拟力
→ 球缘接触点施力
→ 球体位置、速度与角速度
```

建议论文明确：`force_max` 是游戏力标度，不是校准后的牛顿。

- `GateDef`：门位置、方向和阈值；
- `SegmentDef`：不可见任务路段；
- `ChoiceForkDef`：岔路入口、方向和确认线；
- 关卡 `.tres` 保存布局、中心线、时限和实验组件；
- WorldBuilder 负责构建可见世界与边界。

### 6.5 自动化验证

历史中建立了以下类型测试：

- 门成功、失败、免伤和防重复触发；
- 关卡布局与通道可达性；
- 岔路和扰动事件；
- 合作物理探针；
- 实验录入和编号；
- 原始数据验证与派生分析；
- 跨 session 汇总；
- 本地化文本。

重要边界：

- 静态 BFS 可达不等于真实玩家能顺畅通过；
- API 接受震动命令不等于马达真实起振；
- 自动化物理探针不等于人类被试效应量。

- `segment_results.csv`：每次闭合路段；

## 9. 当前预实验方案

### 9.1 定位

这是 **feasibility pilot**，目标是验证：

- 流程是否能一次走完；
- 时长和疲劳是否可接受；
- 手柄、分屏和日志是否可靠；
- 五关是否可玩；
- 第 4 关干扰是否可感知且可计算；
- 原始三表和跨组汇总是否完整。

不用于：

- 显著性检验；
- 正式功效分析；
- 宣称扰动因果效应；
- 将第 3、4 关包装为严格对照；
- 将方案称为随机对照实验。

### 9.2 样本建议

- 首轮 6–8 个 dyad（12–16 人）；
- 依据是覆盖流程变异和异常类型，不是统计功效；
- 若连续两组仍出现新阻断问题，再扩至 10–12 个 dyad；
- 当流程可重复、质量门槛达标且无新阻断类型时停止扩组。

### 9.3 流程

```text
知情同意
→ 录入组号与关系
→ 配对与输入检测
→ 教学关
→ 第 1–5 关
→ 简短访谈
→ 数据质检
```

游戏不会强制锁定 1→5 的顺序，当前依赖研究员遵守 SOP。

### 9.4 质量门槛

- 纳入 session 的原始三表完整率 100%；
- `session_id` / `trial_id` 不冲突；
- 至少 90% trial 有 `trial_end`；
- 第 4 关有预期 `perturb_on`；
- A/B 受扰侧基本平衡；
- 非 `ok` 质量试次进入人工复核；
- 因设备或流程无法继续的比例低于 20%；
- 所有偏离和排除都有记录。

## 11. 已否决或被替换的方案

### 11.1 物理与交互

- **直接设置球速度**：违背施力和摩擦的设计目标；
- **隐藏合作增益倍率**：不可感知、不可解释；
- **高角阻尼快速消除失配旋转**：使任务退化为同向满推；
- **离散输入档位惩罚满推**：损失连续控制信息；
- **一律向右的地面箭头**：在纵向路段误导玩家；
- **在结算显示个人贡献排名**：破坏合作导向。

### 11.2 触觉

- **按速度突变猜碰撞**：摇杆输入本身会造成误触发；
- **持续移动微震**：Switch Pro 上形成狂震；
- **接触后按求解速度判断碰撞**：求解后速度可能接近零；
- **RumblePak 插件**：底层持续重启震动；
- **仅用 API 回读判断真实震动**：只能确认命令状态，不能确认马达或人的感知。

### 11.3 关卡

- **L4/L5 仅复用 L2/L3 骨架**：拓扑相似、缺乏新合作行为；
- **过窄通道作为主要难度**：造成卡球而非协调；
- **固定可预测扰动节奏**：玩家可学习时间表；
- **显式实验区域、风险标签和投票界面**：破坏连续游戏体验；
- **每关堆叠多机制**：使行为解释混杂。

### 11.4 实验设计

- **全局 Baseline/Perturbation 分组**：已从当前 pilot 删除；
- **把第 3 关当作第 4 关严格 baseline**：两关地图和任务不同；
- **把质量阈值直接当自动排除**：现改为 flag + 人工复核；
- **把物理帧当独立样本**：违反数据层级；
- **把 feasibility pilot 写成正式因果实验**：不成立。

### 11.5 编号与数据表

- 自由文本参与者 ID；
- `D001` 编号；
- 将采集站编码进 dyad ID；
- 13 张表全部默认导出；
- 默认生成大型人工复核窗口表；
- 用 `0` 代替未知或删失数据；
- 手工拼接各 session CSV。

## 12. 关键失败、纠错与方法学启示

### 12.1 双重除以 Fmax 导致球推不动

**问题**：输入映射中重复缩放，导致最终力过小。  
**启示**：连续输入链路应在每个阶段保留可观测中间值，并通过端到端探针验证。

### 12.2 门在键盘测试正常、手柄新手过难

**问题**：开发输入设备与目标实验设备不同。  
**启示**：任务参数必须在实际参与者设备、实际双人条件和新手群体上标定。

### 12.3 静态可达但实机体验差

**问题**：BFS 只证明几何路径存在，无法证明惯性球体易于通过。  
**启示**：关卡验证需分为几何可达、物理可达和人类可玩三个层次。

### 12.4 自动震动断言通过但无法证明真实触感

**问题**：`get_joy_vibration_strength()` 回读调用值，不是马达传感器。  
**启示**：触觉操纵必须有实机主观检查；连接方式需纳入设备记录。

### 12.5 通关或失败瞬间卡顿

**问题**：同步全量派生分析绑定 trial 边界。  
**启示**：原始数据保存、派生分析与结算反馈应解耦；性能问题也可能成为实验效度问题。

### 12.6 编号规则多次重构

**问题**：组号、关系和采集站曾被混合编码。  
**启示**：研究标识符应分别表达稳定实体和上下文，不把多种语义塞入一个字符串。

## 13. 当前已知有效性风险

### 13.1 内部效度

- 第 3 与第 4 关在地图、任务和顺序上不同；
- 无 sham 干扰；
- 五关固定顺序可能产生学习、疲劳和携带效应；
- 选关顺序由实验员执行，软件未强制；
- 近期门难度和时限仍在调参；
- 同步导出卡顿可能改变 trial 末段体验。

### 13.2 构念效度

- 方向一致性不等同于合作质量；
- 领导者算法是多个指标的操作化，不是人格领导力；
- 路线纠偏贡献不等同于干扰补偿反应；
- 路线选择可能同时受风险偏好、操作熟练度和剩余时间影响；
- 朋友/陌生人是自报类别，未独立验证关系强度。

### 13.3 外部效度

- 当前主要在 macOS 和有限手柄型号上验证；
- Xbox 在 macOS 上 USB 连接无法提供震动，蓝牙可用；
- 键盘与手柄的连续输入能力不同；
- 自动化测试和开发者试玩不能代表目标参与者；
- 当前 ad-hoc 签名应用不等于可公开分发或公证版本。

### 13.4 统计结论效度

- 预实验样本量不是按效应量和功效确定；
- 帧级观测高度自相关；
- 多个探索性指标可能带来多重比较；
- 恢复时间存在右删失，不能把未恢复写成 0；
- 组件专项表部分字段历史上仍是占位实现，分析前需核对。

## 14. 平台与设备经验

### 14.1 Xbox 震动

**已验证结论**

- macOS 下 Xbox 手柄通过 USB 连接时，Godot 无法获得预期震动；
- 改为蓝牙后，两把 Xbox Series X 手柄均由用户确认可以震动；
- 因此该次故障不是游戏震动链路整体失效。

**论文/实验要求**

- 记录手柄型号、连接方式和操作系统；
- 正式实验前执行真实触觉检查；
- 不以 API 断言代替操纵检查；
- 纯键盘条件没有触觉反馈，不能与手柄条件默认为等价。

### 14.2 Switch Pro

- Nintendo 面键布局需要单独映射；
- 持续输入时可能吞掉同帧短震动；
- 实现中采用停震、等待帧和延后脉冲的 workaround；
- 原生 HD Rumble 插件曾被讨论，但未成为当前依赖。

### 14.3 macOS 打包

- 项目已有 macOS 导出配置；
- Godot hardened runtime 导出曾导致双击启动失败；
- 通过 ad-hoc 重签脚本修复本机运行；
- 该方案不等同于 Apple 公证和广泛分发。

## 16. 可用于论文的贡献候选

以下仅是候选贡献表述，需根据最终研究问题和数据收窄：

### 16.1 交互系统贡献

一种把双人连续输入映射为同一球体轮缘接触力的协作控制任务，使平移、旋转、冲突和补偿由可解释的物理耦合产生。

### 16.2 任务设计贡献

一套由共同起步、共同减速、弯道协调、失衡补偿和路线选择构成的五关渐进任务，每关聚焦一种主要 dyadic behavior，同时保持连续游戏体验。

### 16.3 测量贡献

一条从原始输入、校准、虚拟力、物理状态到事件级和试次级协调指标的可重算数据管线，并显式处理版本、删失、质量标记和跨 session 汇总。

### 16.4 设计方法贡献

项目迭代揭示了实验游戏开发中的四类常见冲突：

1. 物理可解释性与快速游戏化增益；
2. 数据完整性与试次边界流畅性；
3. 自动测试与真实人类/设备体验；
4. 实验可测性与玩家对实验结构的察觉。

## 19. 仍需通过预实验回答的问题

### 19.1 可玩性

- 新手是否能在教学关理解门？
- 门是否仍要求真实双人合作，又不会长时间卡关？
- 第 3–5 关 180 秒是否过长或仍不足？
- 完整五关实际需要多久？
- 后半程失败和退出是否过多？

### 19.2 操纵

- 第 4 关干扰是否可感知但不可精确预测？
- 干扰是否足以诱发补偿，又不会必然撞墙？
- A/B 受扰顺序是否平衡？
- 干扰前 200 ms 是否有足够稳定基线？

### 19.3 测量

- 自动补偿起点与人工标注是否一致？
- 恢复判据是否过严，导致大量右删失？
- 门、弯道和岔路事件是否能从原始数据重算？
- 55 Hz 和 5% 丢帧阈值是否适合实际设备？

### 19.4 体验与设备

- 触觉反馈在目标手柄上是否稳定？
- 键盘与手柄难度差异是否需要限制输入设备？
- 同步导出卡顿修复后是否消失？
- 玩家是否感到自己在玩连续滚球冒险，而不是完成实验题目？

## 20. 可直接转写为论文段落的观点草案

### 20.1 物理设计

Dyadic Force 没有把两名玩家的输入直接转换为球体目标速度，而是将经校准的连续方向输入映射为作用于球体轮缘的虚拟力。该处理使同向输入主要贡献平移，反向或失配输入自然产生扭矩、偏航与打滑，并允许闲置侧通过接触摩擦形成可解释的阻力。由此，双人优势来自可感知的力叠加与协调，而非隐藏的合作倍率。

### 20.2 关卡设计

五个正式关卡分别围绕共同起步、共同减速、弯道协调、失衡补偿与路线选择构建。设计避免在单关内堆叠多种新机制，而通过同一能力的自然重复获得事件级样本。除可撞门外，路段标注、扰动触发和岔路识别均对玩家不可见，以降低实验结构对自然游戏行为的干扰。

### 20.3 数据设计

系统将不可覆盖的 session、frame 和 event 原始记录与可重算的派生结果分离。逐帧数据保存参与者身份映射后的输入链路、最终虚拟力、球体状态和路线误差；离散事件记录试次结局、碰撞、门、路段、扰动和岔路行为。分析器进一步在 trial、component 与 perturbation 层级计算协调、补偿、恢复和选择指标，并通过版本化 manifest 和跨 session 汇总保留审计能力。

### 20.4 预实验边界

当前 pilot-1.0 被定义为单次可行性预实验，用于验证流程、时长、可玩性、扰动可感知程度和数据完整性，而非检验干扰的因果效应。第 3 关提供正常协调参考，第 4 关固定包含真实干扰，但由于两关在地图和任务上不同，二者不能构成严格对照。补偿与恢复因此以每次干扰前 200 ms 的局部行为作为基线。

## 22. 最重要的写作警告

1. 不要把当前 pilot 称为随机对照实验。
2. 不要把第 3 关称为第 4 关的严格 baseline。
3. 不要把可行性样本量解释为功效充分。
4. 不要把假名化数据称为匿名数据。
5. 不要把帧当作独立样本。
6. 不要把建议、静态审计或未运行测试写成已验证事实。
7. 不要把自动震动 API 断言写成参与者确实感知到触觉。
8. 不要把开发者物理探针数值写成人类行为效应。
9. 不要把当前软件能力写成已有研究结果。
10. 在正式收数前重新核对近期未提交改动、时限、门阈值与扰动时序。
